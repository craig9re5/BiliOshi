# 自动投喂粉丝团灯牌：调研与离线原型

调研日期：2026-10-09。状态：**研究原型，未接入自动任务或桌面送礼**。灰度期间不启用，不在 UI 展示投喂入口或灯牌投喂任务；离线规划工具保留。

## 1. 结论和证据边界

自动投喂在技术上有可参考的实现：读取直播间礼物面板，选择礼物，再调用购买送礼或背包送礼接口。我们当前拥有扫码会话、账号认证、WBI 签名、任务查询和统一 HTTP 边界，具备继续开发的基础。

但以下三件事必须独立核验：

1. 赠送的是否是当前房间每日 `feedLight` 任务要求的灯牌。
2. 礼物是否真的发送、扣费多少，是否出现结果未知的订单。
3. `feedLight` 是否从 `0/1` 变为 `1/1`，亲密度是否随后结算。

接口 `code=0`、粉丝牌已点亮、包裹里有礼物，都不能分别替代这三项核验。本轮没有发送礼物，没有购买、充值，也没有更换登录会话。

### 当前匿名礼物面板观察

通过不携带 Cookie 的 `GET /xlive/web-room/v1/giftPanel/roomGiftList` 查询，两个房间均出现：

| 名称 | ID | 原始单价 | 币种 | 所在面板 |
| --- | ---: | ---: | --- | --- |
| 粉丝团灯牌 | 31164 | 100 | gold | `gift_data.room_gift_list.gold_list` |
| 粉丝团灯牌 | 34001 | 100 | gold | `gift_data.tab_list[].list` |
| 专属灯牌 | 35561 | 5000 | gold | 标签页列表 |

这些数值是查询时的公开配置，**不是固定协议常量或针对其他房间的承诺**。两个同名 ID 都有实际面板位置，不能靠“取配置列表第一个”决定发送哪个。需要用正常投喂成功记录确认目标 ID 与每日任务的对应关系。

当前候选标价为 `gold`，应按涉及付费余额的礼物处理。尚未找到可验证的免费领取灯牌并完成此每日任务的路径；这不等于证明免费活动永远不存在。背包接口中的 `price=0` 表示一种请求构造，不能证明背包礼物免费获得或具备 `feedLight` 资格。

参考实现的电池换算与[社区 API 文档](https://github.com/pskdje/bilibili-API-collect/blob/main/docs/live/gift.md)的人民币换算存在差异。因此原型预算只使用接口原始整数单位，不硬编码人民币金额，也不根据旧规则硬编码“每次必得 +6”。显示实际金额和预计奖励前，需要核验当前网页价格、消费流水及任务说明。

### 代码检查发现的具体问题

- 礼物调度示例按名称 `find` 配置项、按名称缓存价格。当前存在同名不同 ID，顺序变化就可能选择另一个礼物。
- 该示例 WBI 获取失败后继续发送未签名请求。正式实现应直接停止，不通过备用请求反复尝试购买。
- 它先购买、遇到“包裹”提示再尝试背包。我们的“仅背包”模式必须独立选择路径，绝不能隐含购买回退。
- 单条指令额度和进程内队列，不能约束多个房间 worker、GUI 手动操作与重启后的总消费。
- tofu 的示例把主播 UID 同时填到 `uid` 与 `ruid`。应分别使用服务端认证的观看者 UID 和房间查询得到的主播 UID。
- 旧赠送接口、活动奖励礼物和现代多收件人接口不能混搭字段；限时活动礼物也不能直接当作常驻粉丝团灯牌。

### 发送路径参考

| 路径 | 开源代码展示的请求形式 | 尚未确认的部分 |
| --- | --- | --- |
| `/xlive/revenue/v1/gift/sendGold` | 礼物助手使用 WBI 签名后的 POST 表单 | 当前网页是否采用相同签名字段集合、query/body 布局与附加场景字段 |
| `/xlive/revenue/v2/gift/sendBagMultiUser` | BLTH 使用签名 query、空 POST body | 灯牌是否在可用背包中、收件人条件及任务资格 |
| 旧 `/xlive/revenue/v1/gift/sendBag`、`/gift/v2/live/bag_send` | 不同历史实现采用表单 | 是否仍适用于当前客户端与礼物类型 |

这张表是源码观察，不是已经实测可用的调用规范。当前原型没有生成完整 POST 数据，也没有将任何路径接入执行器。

重要字段：

- `uid`：已认证的观看者，不能从主播 UID 替代。
- `ruid`：主播 UID；`biz_id`：真实直播间号，不能混用。
- `gift_id`：经面板和成功任务记录共同确认的灯牌候选。
- `gift_num`：首版固定为 1，不按亲密度缺额批量购买。
- `price`、`coin_type`：当前报价及币种，执行前复核。
- `bag_id`：只有背包路径使用；不凭空填入以“免费发送”。
- CSRF、WBI、会话头：复用现有匹配账号的扫码会话和签名实现，不要求用户公开 Cookie。
- 订单/发送标识、实际消耗：保存脱敏结果以便核对，不能只记录 `code=0`。

**现有项目没有自动投喂灯牌。** `DailyTaskRunner` 只执行弹幕与点赞；GUI 展示“灯牌”不意味着已有发送实现。`is_lighted` 是勋章点亮状态，也不是 `feedLight` 已完成。此前将自动点亮解释为自动赠送灯牌的说法不准确。

### 不影响看播心跳

当前心跳和周期任务存在同步调用关系。礼物查询、下单、等待结算不能继续塞进心跳回调并长时间阻塞。应由独立账号动作队列处理，任务查询按计划短时执行，结果写回统一状态；心跳继续遵循服务器间隔。

## 5. 本轮原型做了什么

核心文件：`bilioshi/services/fan_light.py`。只负责纯数据计算：

1. 严格解析唯一的 `jump_type=feedLight`，校验 `0/1`、`1/1` 与 `is_done` 一致；异常、缺失和规则变化返回不可核验。
2. 从 `gift_config.base_config.list` 取得精确名称和报价，再与已知房间列表、标签页实际位置相交。排除“专属灯牌”、未上架配置、隐藏价格和未知支付场景。
3. 明确要求选择经过正常投喂记录核验的 gift ID，单一候选也不等于任务资格已验证。
4. 检查服务端认证标记、目标房间授权、在播状态、保护状态、快照时效和 UTC+8 日期。
5. 将已消费与尚未释放的预留都计入账号预算；已有当日尝试或存在未知订单时停止规划。
6. 生成固定一件的不可变预览；`execution_allowed` 恒为 `false`。
7. 对照投喂前后任务，区分已受理但未结算、任务已完成、消费仍未知、原本已满和跨日不可核验。

亲密度差值作为同期观察单独返回。它可能同时包含看播、弹幕或其他来源，不自动归因给灯牌，也不将差值为零判定成发送失败后补送。

## 6. 正式接入的建议状态机

```text
未启用 / 未授权 / 无法核验 → 展示原因
任务已完成 → 跳过
任务未完成 → 最新礼物与价格校验 → 账号锁内预留预算
  → 持久化 reserved → 单次提交
    → 明确拒绝：记录失败、释放可确认未扣费的预留
    → 超时、断连、响应无效：unknown，冻结后续投喂并只读核对
    → 接口受理：submitted，等待订单与任务核验
      → 订单及消费确认 + feedLight 完成：confirmed
      → 订单确认但任务未完成：提示资格/结算异常，禁止补送
```

关键约束：

- 使用已认证 UID + UTC+8 日期 + 真实房间号 + `feedLight` 作为本地防重键。
- 本地键不等于平台支持幂等请求；无法保证“提交后崩溃”可安全重试。
- 同一 UID 的 GUI、CLI、多个 worker 共用账号锁和账本。预留检查及写入必须在锁内原子完成。
- 重新扫码、程序重启和跨日不清除尚未核清的消费；不同日期的预算独立，未知订单保护持续。
- 消费账本损坏或无法读取时停止投喂，不能恢复成空账本。
- 首版每个授权房间每日最多尝试一次、每次一件；明确拒绝也不在当日自动再尝试。
- 礼物 ID、单价或收件人变化应重新核验。价格增加超过上限时拒绝，不替换成同名贵礼物。
- 背包模式与购买模式独立，背包失败不能自动改为付费；免费活动路径须单独验收。
- 账号风控、登录过期、权限限制统一进入已有保护。保护解除也不清除未知订单状态。
- 桌面与命令行调用同一个计划、账本和执行服务；桌面只展示和配置。

建议 GUI 默认“关闭”，逐步提供“仅已核验背包”和“限额购买”两种显式策略。显示授权房间、当前报价、账号每日额度、预留额度、最近投喂状态和结算时间。任务“未完成”不能被模糊成“执行失败”。

## 7. 分阶段推进与验收

### A. 已完成：研究与离线规划

- 阅读购买送礼、背包送礼和勋章点亮代码，对照本项目调用链。
- 匿名查询公开礼物面板，发现并验证两个同名候选的结构。
- 原型与回归测试；不接入账号动作、程序安装或自动发布。

本轮验证：新增 24 项回归测试，全项目 211 项离线测试通过；架构检查无错误，公开文件与 Git 历史扫描无发现。匿名取得的当前礼物面板也通过新解析器，识别出两个不同位置的灯牌候选。这些结果不包含账号赠送或奖励到账验收。

### B. 下一步：只读探测与一次正常投喂对照

先增加通过 `AppContext` 调用的只读探测器：任务基线、已认证身份、房间归属、当前面板、如需使用则查询背包和钱包。报告仍保存在被忽略的 `build/`。

决定实际测试前展示一个具体方案：目标房间、礼物 ID、数量 1、网页实际价格及消费上限。需要正常成功的请求、响应、实际消费、任务前后值；抓包应清理 Cookie、CSRF、签名、设备字段和私人账号资料。无需将完整会话贴入对话。

由这个对照确定：

1. 31164 / 34001 中实际提交哪个，是否存在客户端差异。
2. 当前签名覆盖的字段和 query/body 构造。
3. 已有勋章用户每日赠送是否完成 `feedLight`，背包路径是否同样有效。
4. 消费单位、实际消耗、结算延迟和当日亲密度上限对奖励的影响。

如果任务接口提示 `reach_free_intimacy_limit`，应先核验灯牌的奖励是否仍可结算。该字段现用于看播诊断，不能未经验证就认定它一定适用或不适用于付费灯牌，也不能保证“任务完成必然还有收益”。

任务必须事先未满；`1/1 → 1/1` 不能证明有效。实际测试不能用反复购买来追查延迟。

### C. 消费账本与单次执行器

核验协议后，再实现持久化原子预留、独立礼物 HTTP 分类、未知订单保护、单次发送和只读结算。离线覆盖多进程竞争、提交后崩溃、扫码换会话、跨日、账本损坏、钱包不足和平台明确拒绝。

### D. 桌面、CLI 与受控自动化

同一业务服务接入独立开关、房间授权、预算编辑和状态提示。确认心跳不会因送礼阻塞。完成单房间、有限预算验收后再考虑多个房间；自动化不购买直到任务收益“刷满”。

### E. 发布准备

保留源码归属；只发布合成测试向量。私人抓包、消费流水和运行报告保持忽略；运行离线测试、架构检查、公开扫描。GUI 变更另做控件测试及构建验证后才发布程序。
