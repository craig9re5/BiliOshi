# 多账号挂机与账号管理方案

> 状态：第一期已审批并实现（单活动账号、免扫码切换、逐账号总览与管理）；第二期“同时挂机”仍待单独审批，暂未实现。
>
> UI 设计稿：[designs/multi-account/Multi-Account.html](../designs/multi-account/Multi-Account.html)

## 1. 结论

**同时挂机技术上可行，但不建议作为默认能力。** 现有代码的数据层已经按数据目录隔离：每个房间 worker 是独立子进程，`safety`、每日预算、任务状态都按账号 UID 分文件。真正的缺口是账号库、进程生命周期、快照契约和 UI，而不是协议层。

建议分两期：

| 阶段 | 内容 | 定位 |
| --- | --- | --- |
| **第一期（推荐先做）** | 账号库、应用内免扫码切换、账号管理、每账号独立直播总览；同一时间只运行一个账号 | 满足最低要求，风险低，先验收账号隔离与数据迁移 |
| **第二期（单独审批）** | 同时挂机：多个账号各自运行一个 Engine；默认关闭的实验开关 | 技术上可行，但平台风控与资源占用都有不确定性，需要单独确认 |

平台条款对自动化工具和多账号都不友好：B 站用户协议禁止使用脚本/自动程序获取服务，并把“多个账号实际控制人为同一人”纳入异常认定。**本方案不宣传“合规”或“不会风控”**，不提供批量注册、账号导入、代理、设备指纹伪造或验证码绕过；只面向用户本人的少量账号。第一期的单账号运行明显比并发更保守。

明确不做：跨机器同步账号、账号共享/出租、按账号切换 IP/设备指纹、批量导入凭证、绕过平台验证。以上任何一项都会把风险从“本机多账号”放大到“规避平台风控”，不属于本方案范围。

## 2. 现状与阻塞点

当前实现是彻底的“单账号单数据目录”：

| 位置 | 现状 | 影响 |
| --- | --- | --- |
| `credentials.json` | 根目录只有一份登录凭证，`save_login()` 直接覆盖 | 切号只能重新扫码；登出会清空全局绑定 |
| `members.json` / `settings.json` | 根目录各一份，不区分账号 | 无法为不同账号保留不同关注列表与任务策略 |
| `Engine` | 一个进程一个 Engine；`account`、`safety`、`paused`、`workers` 都是单值 | 多账号会互相覆盖状态；凭证变化会停掉全部 worker |
| `state/<room>.json`、房间 Mutex、`_room_operations` | 只按房间号做键 | 两个账号关注同一房间会互相阻塞或覆盖状态 |
| `snapshot` / React | 顶层只有一份账号、rows、任务与保护状态 | 无法同时表达多个账号的总览 |
| 启动/托盘/守护 | `tray_app` 用根 `credentials.json` 判断是否已登录；supervisor 只读根 `monitor-health.json` | 账号根与安装根分离后，退出、重启和健康判定会走错目录 |

可复用的基础比想象中多：

- 凭证已经用 Windows 用户级 DPAPI 密封（`bilioshi/secret_store.py`），每个账号复制一份密封文件即可，不需要新的加密方案。
- `safety` 的保护暂停、每日发送额度、任务状态已经按 `uid-<mid>` 分文件，账号切换不会丢额度。
- `Engine.spawn()` 已经给每个 worker 注入 `BILIOSHI_APP_DATA`；只要每个账号有独立数据根，worker/probe 协议几乎不用改。
- `Bridge` 从不接收凭证；账号列表只读密封信封是否存在，不解密。

## 3. 方案选型

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| **A. 每账号独立数据根 + 每账号 Engine** | `accounts/<uid>/` 各自保存凭证、关注、设置、状态、日志；每个账号一个 Engine 和独立 Job | **推荐**。隔离最彻底，复用现有 worker/probe；第一期只激活一个 Engine，第二期扩展为多个 |
| B. 单根账号作用域 + 单 Engine 多账号会话 | 所有账号共用根目录，Engine 内部按账号分桶 | 不推荐第一版。要重写 Engine 的 workers/retry/safety/快照几乎所有字段，root 级锁仍会串行化账号，主要资源（worker 子进程）也不减少 |
| C. 多开独立进程/实例 | 每个账号一个 `BILIOSHI_APP_DATA` 启动一套桌面 | 只适合作为排障兜底。会出现多个窗口、多个托盘、多个守护和自动启动冲突，不是产品方案 |

还有一个迁移变体：**首选账号继续驻留安装根**，只有新增账号进入 `accounts/<uid>/`。它的迁移成本最低、旧版回滚最直接，但会让账号 Engine 与 Controller 共用安装根的 `settings/status/monitor-health`，移除首选账号还需要特殊分支，违背“安装根只放应用级状态”的边界。因此不采用；本方案把首个账号也复制到 `accounts/<uid>/`，旧根原样保留作为回滚备份。

## 4. 推荐架构（第一期）

### 4.1 目录与数据模型

```text
<安装数据目录>/
  state/accounts.json          # 账号注册表：只存公开元数据，绝不存凭证
  accounts/
    uid-41278891/
      credentials.json         # DPAPI 密封，一个账号一份
      members.json             # 该账号的关注列表
      settings.json            # 该账号的任务策略与暂停状态
      state/
        <room>.json            # 该账号的房间连接状态（沿用现有文件名）
        tasks/                 # 该账号的每日任务额度
        safety/                # 该账号的保护暂停记录
        account-avatar.json    # 该账号的公开头像缓存
        last-snapshot.json     # 停用后供总览展示的脱敏快照
      logs/activity.jsonl
      locks/
    .retained/uid-41278891/    # 账号移除后保留的关注、设置、任务额度、保护记录与绑定（不含凭证）
  monitor-health.json          # 安装根：由 Controller 写，supervisor 只读这里
  supervisor-*.json            # 安装根：桌面生命周期
  logs/desktop.log             # 安装根：桌面日志（带 account_id）
```

`state/accounts.json` 建议结构：

```json
{
  "version": 1,
  "mode": "single",
  "global_paused": false,
  "active": "uid-41278891",
  "view": "uid-41278891",
  "accounts": [
    {
      "id": "uid-41278891",
      "uid": 41278891,
      "name": "夜航星",
      "face": "https://i0.hdslb.com/...",
      "created_at": 1770000000,
      "last_used_at": 1770000000,
      "last_checked_at": 1770000000,
      "status": "ok",
      "watch_enabled": false,
      "credential_token": "mtime-size",
      "data_dir": "accounts/uid-41278891"
    }
  ]
}
```

规则：

- `id` 只由服务端生成（`uid-<mid>`），不接受 renderer 传路径或任意字符串。
- 注册表只存 `uid/name/face/时间/状态` 等公开信息；`SESSDATA`、`bili_jct`、`qr_login_context` 永远只在密封文件里。
- `credential_token` 只是文件 `mtime_ns:size`，用于缓存失效，不是秘密。
- 账号以 B 站 UID 唯一化；同一 UID 重新扫码只更新该账号的凭证，保留关注列表、任务额度和保护记录。不同 UID 才能新增。
- `mode`、`global_paused`、`watch_enabled` 是调度状态，与账号设置里的用户暂停分开；`watch_enabled` 只在第二期生效。
- `active` 是安装根 `status.json`、托盘和 CLI 跟随的账号；`view` 是界面当前查看的账号。单账号模式两者通常相同；同时挂机模式 `active` 只是兼容入口，真正运行集合由 `watch_enabled` 决定。
- 安装根 `settings.json` 只保留应用级偏好（`autostart`、主题等）；`mode` / `global_paused` 以注册表为唯一真源，不写入 `settings.json`。任务开关、账号级运行策略、账号暂停写入账号根 `settings.json`。迁移时要把旧根的这些字段分流，不能留下两处真源。
- 注册表使用原子写并保留上一版 `.bak`；损坏时先读 `.bak`，再失败则进入安全模式，不自动扫描目录启动任意账号。

### 4.2 安装根与账号根分离

这是本次改造最重要的边界：

- **安装根**只承载账号注册表、supervisor/desktop 生命周期、Controller 健康文件、全局外观和开机启动。任何账号 Engine 都不能使用安装根作为数据目录。
- **账号根**承载该账号的全部可变状态。`Engine(account_root)`、`AppContext(account_root)`、worker/probe 的 `BILIOSHI_APP_DATA` 都指向账号根。
- `WebHost` 必须显式持有 `host_root`（安装根）；退出、命令轮询、supervisor IPC、日志入口都走 `host_root`。账号 Engine 的 `root` 只用于数据和子进程环境。

### 4.3 Engine 生命周期与所有权

- 新增 `AccountHost` / `AccountManager`（位于 `desktop/`）：维护 `account_id -> Engine`、当前查看账号、活动账号集合与并发开关，替代 `tray_app` 里直接 `Engine(root)` 的路径。
- **每个账号的 Engine 拥有自己的 `Job`**。不要为了统一退出共享一个由 `Engine.close()` 负责关闭的 Job：Job 设置了 `KILL_ON_JOB_CLOSE`，任一 Engine close 会杀掉全部账号的 worker。
- `Engine` 目前不能二次 `start()`，因此**切号优先使用“挂起/激活”，不要每次 close/start**：
  - 新增内部状态 `suspended`（与用户可见的 `paused` 区分）：挂起时停止 worker/probe、跳过凭证读取与检查，但 monitor 线程和 Engine 对象保留。`paused` 仍是用户保存在 `settings.json` 里的暂停状态，两者不能混用。
  - Engine 在账号第一次被激活时按需创建，之后保留；切换 = 挂起旧账号 Engine → 激活目标 Engine → `check_now()` → 更新 view。整个过程不扫码、不重建 Engine。
  - `suspended` 必须同时拦住 `tick` 的 probe spawn 和 `_apply_probe` 的 worker spawn；挂起时递增 generation、丢弃在途 probe 结果，确保切换后不会出现旧账号的新 worker。
  - 只有新增/移除账号、或该账号凭证被重新扫码替换时才 close 并重建该账号的 Engine；重建时使用新的 Job 和新的 Engine 对象，不复用已停止的线程。close + join 超时则隔离（quarantine）该账号，绝不并发启动同一 root 的第二个 Engine。
  - 挂起账号不启动 `DailyNotifications` 线程；重新激活时按账号启动，避免 N 个账号的空闲通知线程和重复日报。
- 账号被移除时：停 worker → 关闭该账号自己的 Job → 关闭 Engine；其它账号不受影响。退出应用时并行停止所有账号的 worker，再统一等待，避免串行 `5s × 房间数` 的退出延迟。
- 每个账号根增加 Engine 单例保护（文件锁或命名 Mutex），禁止同一账号根出现两个 Engine；同一账号被复制到两个根要由注册表唯一化直接拒绝。
- 每个账号做独立 watchdog：某个账号的心跳/调度卡住只重启该账号 Engine，不触发整个桌面重启。

### 4.4 守护与健康

- `monitor-health.json` 改为由 **AccountHost** 写在安装根，字段保留 supervisor 需要的 `pid/started/updated/last_tick/last_status_publish/publish_error`。账号 Engine 的卡顿写账号根自己的 `engine-health.json`，由 AccountHost 汇总，不再让 supervisor 依赖某个账号。
- Host 使用**独立健康线程**写安装根健康文件；停止账号、并行 terminate worker、设置变更期间健康文件仍持续更新，避免一次长 tick 超过 supervisor 的 90 秒阈值而重启整个桌面。每个账号另有 watchdog，只重启该账号。
- 账号根写自己的 `status.json` 与 `engine-health.json`，带 `account_id/engine_started/engine_state`。安装根另写一份当前活动账号的 `status.json` 镜像，保留现有 CLI/外部读取的兼容行为。外部读取必须区分“应用退出”和“某账号停用”。
- 托盘与 `--command` 仍作用于安装根；新增账号级命令时显式带账号 id。退出应用仍然只由安装根决定。
- 兼容入口：`BILIOSHI_APP_DATA` 继续可以指向一个账号工作目录；不指定时，CLI 默认使用注册表中的活动账号（迁移前则使用旧根）。需要指定其它账号时增加显式 `--account <id>`，不要靠猜测目录。`setup_local_cookie.py` 与日报同样默认活动账号；多账号日报的聚合留到第二期。

### 4.5 快照与桥接契约

保留顶层为**活动账号**的旧快照，托盘、Tk 和现有测试不需要重写；新增账号维度：

```json
{
  "schema": 2,
  "active_account_id": "uid-41278891",
  "view_account_id": "uid-52801146",
  "mode": "single",
  "global_paused": false,
  "accounts": [
    {
      "id": "uid-41278891",
      "uid": 41278891,
      "name": "夜航星",
      "signed_in": true,
      "running": true,
      "paused": false,
      "watch_enabled": false,
      "safety": { "blocked": false },
      "room_count": 4,
      "live_room_count": 2,
      "state": "running",
      "state_label": "挂机中",
      "snapshot_at": 1770000000,
      "stale": false
    }
  ],
  "view": { "...": "与顶层同构的查看账号快照，仅 view != active 时附带" }
}
```

- 顶层仍是活动账号的完整快照（`rows`、`accountInfo`、`paused`、`safety`、`settings`、`recovery`），旧调用不变。
- `accounts[]` 只放轻量摘要；`view` 只在查看账号不是活动账号时附带，避免每 0.75 秒推送 N 份完整 rows。
- 每个账号的 `rows`、`medals`、`tasks` 留在自己的子快照里，不合并成全局 map；所有 row 带 `account_id`。
- 操作键改为 `(account_id, room)` / `(account_id, kind)`；同一房间被两个账号关注时不会互相阻塞。
- 非活动账号的 `view` 优先读 `accounts/<uid>/last-snapshot.json`，统一标记 `active=false`、`live_status=null`、`status_stale=true`、`tasks_stale=true`，所有操作带明确原因（“账号未运行，请先切换”）；绝不把旧数据伪装成实时。
- 新增端点：
  - `set_view_account(id)`：只切换查看，不动物理运行；
  - `switch_account(id)`：第一期切换活动账号（挂起/激活 Engine），第二期在并发模式下只切 view；
  - `qr_start(account_id=None)`：`None` 新增账号，指定 id 重新登录该账号；
  - `remove_account(id)`；
  - `account_avatar(id)`：只接受注册表 id；
  - 第二期增加 `set_account_concurrent(id, bool)`。

### 4.6 切换流程（免扫码）

**查看与挂机是两条独立的轴。** 顶部账号标签、总览卡片和“打开总览”只切换查看，不停止也不启动任何连接；未运行账号显示 `last-snapshot` 并标记陈旧。换挂机账号必须走侧栏切换器的“切换挂机账号”或账号页的“切换并挂机”。

第一期单账号模式“切换并挂机”：

1. 用户在侧栏切换器或账号页选择目标账号，点击“切换并挂机”。
2. 若当前已有账号在挂机，先显示双账号对照确认（旧账号暂停 / 目标开始，连接会短暂中断，不扫码）；确认后才执行。
3. Python 先检查：没有正在执行的房间操作、没有正在扫码、应用未在退出；否则返回 busy，并提示等待。
4. 先解封并验证目标账号凭证；失败则**不停止当前账号**，标记目标 `needs_login`，提示单独“重新扫码”。
5. 挂起当前 Engine（停止 worker/probe，不再发请求），递增 generation 丢弃在途 probe 结果。
6. 激活目标 Engine；目标凭证在账号根内，直接使用，**不弹二维码**。
7. `check_now()` 重新查询直播状态；界面显示“正在切换到 X…”，随后显示新的总览。启动失败则回滚到旧账号，旧账号继续挂机。

需要明确的语义：

- “免扫码”不等于“零中断”：切换挂机账号会停止旧账号的看播连接并重新检查；这只是不需要重新登录。
- 只想看另一个账号时使用顶部标签，不产生连接变化，也不会停掉正在挂机的账号。
- 切号不会重置每日额度、任务进度或账号保护记录。
- 用户主动暂停、全局暂停、“未参与同时挂机”、保护暂停是四种不同状态：账号设置里的 `paused`、应用级 `global_paused`、注册表里的 `watch_enabled`、账号安全状态 `protection`，UI 必须分别表达，不能用同一个“暂停”文案。
- 添加账号成功后不自动启动、也不替换当前运行账号；提示“已添加，可切换并挂机”。只有第一个账号会自动成为查看对象并提示开始挂机。
- 重启时恢复上次查看账号和单账号模式下的上次挂机账号；同时挂机只恢复 `watch_enabled` 的账号，并错峰启动。

### 4.7 设置、关注与数据归属

| 数据 | 归属 | 说明 |
| --- | --- | --- |
| 关注列表、粉丝牌、任务进度、今日亲密度 | 每账号 | 不同账号关注不同主播；同一主播允许出现在多个账号列表 |
| 自动任务开关、账号级运行策略、暂停状态 | 每账号 | 每个账号可以有不同的互动策略 |
| 界面主题、开机启动、并发总开关/全局暂停（注册表）、账号上限 | 全应用 | 与具体 B 站账号无关；注册表是调度开关的唯一真源 |
| 账号保护、每日发送额度 | 每账号（按 UID） | 移除账号也保留，避免通过移除重置额度 |
| 日志 | 每账号 activity + 安装根桌面日志 | 桌面日志带 `account_id`；UI 可看当前账号或全部 |

设置页顶部必须显示“应用对象：账号名”，避免用户以为改了全局。外观标注“全应用”。

### 4.8 通知、托盘与日志

- 第一期只有活动账号在运行：通知、托盘、看播提醒都跟随活动账号；切换时先停旧账号通知线程，再启动目标账号的。
- 第二期使用全局通知协调器：
  - 开播提醒按 `(account_id, room, session_id)` 去重；
  - 日报默认合并为一条“多账号摘要”，避免 PushPlus 每日 100 次限制；
  - 单账号的保护暂停、登录失效单独提示，并带账号名；
  - 一个账号的通知失败不能阻塞其它账号。
- 托盘显示聚合状态（“2 个账号挂机中 · 4 个直播间”），菜单按账号分组提供暂停/检查/打开日志；不做多托盘。

### 4.9 迁移与回滚

首次启动新版本：

1. **预检与备份**：若 `state/accounts.json` 已存在，直接使用。否则读取旧根 `credentials.json`，把密封字节复制到 `state/backup/legacy-credentials-<时间>.json`（只备份密封文件，不产生明文），再解封并通过 nav 取得 UID、昵称、头像。网络不可用时进入“旧版兼容模式”，继续以单账号方式运行旧根，提示“账号库迁移等待网络”，下次启动或手动重试；不能因为迁移失败把已有登录变成未登录。
2. **创建账号根**：创建 `accounts/uid-<uid>/`，**复制**（不移动）旧 `members.json`、`settings.json`、日志和与当前 UID 相关的 `state/`：
   - 只复制 `account-bindings` 中指向该 UID 的映射、`safety/uid-<uid>.json`、`tasks/uid-<uid>-*.json`、`watch-credit-uid-<uid>.json`，以及 `account_key` 为空或等于该 UID 的房间状态；
   - 其他 UID 的 safety/tasks/room state 留在旧根，不复制、不删除；
   - 旧 `activity.jsonl` 不合并进新账号日志；如需保留历史，复制为账号根 `logs/legacy-activity.jsonl` 并在界面标注“旧记录”，避免把其它账号的历史混入；
   - 不复制 supervisor/commands/monitor-health/desktop-process/notifications 等安装根文件；
   - 旧根 `settings.json` 中的任务开关、`run_mode`（稳定/激进）、账号暂停复制到账号根；`autostart` 等应用级字段留在安装根。单账号/同时挂机是应用级 `mode`，不来自账号 `run_mode`。
3. **写入凭证并验证**：在内存中解封旧凭证，确认 SESSDATA/bili_jct 对与 nav UID 一致后，用 `save_login()` 重新密封写入账号根 `credentials.json`；回读、解封、比对。不要把已密封的 envelope 直接再传给 `write_json`（会双重密封）。旧 envelope 的 keyring reference 暂不 discard，保留旧文件用于回滚。
   - **扫码添加/重新登录必须走只读验证路径**：不能直接复用会在当前 root 上调用 `safety.observe → bind_account/hold_account` 的 `validate_credentials_profile`，否则新增 B 会把 B 的 fingerprint 写进 A 的 bindings，或把 B 的失败 hold 写进 A。应在丢弃式临时 root 中验证，或新增不写 safety 的验证函数；确认 `nav.mid == target_uid`、`context.DedeUserID` 与 SESSDATA/bili_jct 一致后，先把凭证写入目标账号根，再在目标账号根上下文中显式 bind。
   - `save_login` / 登出只删除目标 fingerprint 的绑定，禁止再清空整个 `account-bindings.json`。
4. **写注册表与标记**：最后原子写 `state/accounts.json`（保留 `.bak`）和 `state/accounts-v1.json`。顺序必须是“账号目录与凭证 → 回读验证 → 注册表 → 迁移标记”；任何一步崩溃都不会留下“注册表指向不存在账号”的半状态。孤立的账号目录只写日志/修复提示，不自动信任。
5. **启动判定**：`tray_app` 是否打开登录页改为看注册表是否有可用账号；旧根 `credentials.json` 不再被当作正常账号来源。迁移后旧根文件只用于回滚与人工恢复，不再参与调度。

回滚：

- 旧版本不识别 `accounts/`，会继续读取旧根；旧根在迁移时未被修改，可以直接回退。
- 提供 `tools/restore_legacy_account.py --account <id>`：解封选定账号的凭证，用 `save_login()` 重新密封写回旧根，可选复制关注/设置；不产生明文中转，并提示迁移后新增的数据不会自动合并。
- 迁移测试覆盖：备份后崩溃、账号目录写入后崩溃、注册表写入前/后崩溃、回读失败、keyring discard 失败、注册表损坏、单账号信封损坏；断言任一步都不丢失旧凭证，迁移可重复执行。

新账号初始化：

- 新账号写入空的 `members.json`，**不再自动灌入默认 5 位主播**，避免新账号一添加就意外挂机。界面显示“添加主播 / 同步粉丝牌”的引导。
- 账号根 `members.json` 缺失或损坏时必须 fail closed（返回空列表/报错），**禁止回退到 `DEFAULT_MEMBERS`**；`initialize` 对账号根显式传 `[]`。测试首次添加账号不会产生任何默认主播的 probe/worker。
- 首次安装且没有任何账号时，显示空状态与“扫码添加账号”，不再默认打开旧式登录页。

### 4.10 安全边界

- 每个账号的凭证单独密封，使用现有 DPAPI（`UI_FORBIDDEN`，不写明文、不回退明文）。
- 账号列表、快照、日志、桥接响应只包含公开信息；`_public()` 继续过滤 `SESSDATA/bili_jct/qr_login_context/cookie` 等字段。
- 列表接口只检查密封信封是否存在，**不解密**；只有切换/重新登录目标账号时才解封该账号。
- 所有账号端点只接受注册表中的整数 UID / 账号 id，拒绝路径、URL 或任意指纹。
- 账号生命周期分三档，UI 不得把它们混成一个“移除”：
  1. **退出登录**：停该账号连接，删除密封凭证，保留账号行、关注、设置、任务/额度、保护记录与绑定；状态变为 `needs_login`，可随时重新扫码。
  2. **移除账号**：停连接、删除凭证与公开资料、移出注册表；把 `members/settings/tasks/safety/bindings` 移到 `accounts/.retained/<uid>/`，重新添加同一 UID 时恢复。普通 UI 不提供清除任务额度/保护记录的入口。
  3. **彻底删除本地数据**：只作为独立维护工具，二次确认并明确会重置每日额度与保护记录；不进入账号菜单。
- 移除当前运行账号不自动启动其他账号；移除最后一个账号后回到“扫码添加账号”的空状态。
- 旧 keyring 引用在替换/移除时清理；DPAPI 只隔离到 Windows 用户，同一 Windows 用户下的其它进程仍可解密，这一点要在文档里写明。
- 日志与错误信息不得回显凭证；账号切换日志只记录账号 id 与公开名称。

## 5. 第二期：同时挂机

### 5.1 启用方式

- 默认关闭；在账号页开启“允许同时挂机”并勾选参与账号后才生效。
- 首次开启弹风险确认，必须勾选“我已了解风险且这些账号均归我本人所有”；少于两个有效账号时禁用总开关并说明原因。
- 开启总开关只让当前正在挂机的账号参与，其余账号默认不参与；新增账号默认不参与、不自动启动。
- 参与（`watch_enabled`）与暂停（账号 `paused`）是两套独立状态：参与开关不修改暂停；账号已暂停但仍可保持参与，只是不会运行。关闭参与且账号正在运行时要先确认会停止连接。
- 建议默认上限 3 个账号，硬上限 5 个；全局在播 worker 默认上限 8 个、硬上限 12 个。超限时拒绝新增并说明原因。
- 暂停、登录失效、保护暂停的账号不启动 probe/worker。

### 5.2 运行时行为

- AccountHost 同时激活多个账号 Engine；每个 Engine 独立 Job、独立 root、独立 safety/预算/日志。
- 启动和检查错峰：全应用同一时刻最多 1 个 probe 在飞；账号按到期时间公平排序，正常间隔 20–30 秒并加抖动；运行模式仍按账号设置。
- 一个账号的失败隔离：登录失效、保护暂停、worker 卡住只停该账号；其它账号继续。
- 全局暂停是应用级覆盖层，不重写各账号的 `paused`；恢复时只恢复暂停前运行集合中仍有效、未单独暂停、未登录失效、未保护暂停的账号。账号级保护暂停和全局保护暂停都不可手动跳过，重新扫码不会解除。
- 跨账号限速：保持每个账号自己的弹幕间隔；如果同一 IP 连续收到 429/-412/验证码，触发“全局保护暂停”，暂停所有账号的写操作并提示，而不是让多个账号一起撞风控。
- 退出时并行停止所有 worker，设置全局 deadline；Job 作为最后兜底。

### 5.3 资源估算

每个在播房间一个常驻 Python worker，源码模式实测约 30–60MB/进程（不含 WebView2）。3 个账号 × 4 个在播房间 ≈ 12 个 worker，约 0.5–0.8GB；5 × 8 ≈ 40 个 worker，8GB 机器风险高。因此默认 3 个账号、硬上限 5 个，并设全局在播 worker 默认 8、硬上限 12；达到上限时优先活动账号，其余按轮转排队，避免一个账号长期饿死其他账号。

### 5.4 平台风险

- 用户协议禁止自动程序/脚本获取服务，并将同一人控制多个账号纳入异常认定；社区规范也禁止脚本与批量操作。
- 未找到“同一设备/IP 多账号”单独条款，但这不构成允许；设备标识、IP、行为都可能用于关联。
- 结论：技术可行，但不能承诺安全；并发只作为默认关闭的实验能力，不作为公开卖点。

## 6. UI 设计

设计稿：[designs/multi-account/Multi-Account.html](../designs/multi-account/Multi-Account.html)

包含：

- **侧栏账号切换器**：当前账号头像/名称/状态/直播数；展开为账号列表，显示每个账号的挂机状态、登录失效、当前查看勾选；底部“管理账号 / 添加账号”；单账号与同时挂机两种模式的提示不同。
- **直播总览**：顶部账号标签（全部 + 每个账号 + 添加），每个标签带运行状态点和直播数；“全部”是账号汇总卡片，选中账号后进入该账号的独立关注列表与详情。
- **账号管理页**：账号卡片（头像、UID、关注数、直播数、今日亲密度、上次检查、登录/保护状态），主操作按状态变化（切换并开始 / 切换查看 / 重新扫码 / 恢复挂机），次级菜单（重新扫码、退出此账号登录、打开日志、移除账号）；“同时挂机”总开关与逐账号参与开关；风险提示。
- **添加/重新登录二维码**：区分“添加账号”和“重新登录此账号”，文案明确不会退出其它账号；扫码到已有 UID 时更新该账号而不是新建。
- **退出登录确认**：删除该账号的本地凭证并停止连接，保留账号行、关注、任务进度、额度与保护记录；重新登录需要扫码，其他账号不受影响。
- **移除确认**：明确会移出列表并删除凭证/公开资料，但保留任务额度与保护记录；不提供“清除额度”的入口。
- **切换确认**：单账号模式下切换挂机账号时，对照显示“当前挂机 → 将暂停 / 目标 → 将开始”，明确连接会短暂中断但不需要扫码。
- **全局暂停**：总览与账号页提供“全部暂停”；它是应用级覆盖层，不重写每个账号自己的暂停状态。恢复时只恢复暂停前正在运行的账号，单独暂停的账号保持暂停。
- **保护暂停**：账号进入保护暂停后显示原因和“打开 B 站安全中心”，明确“重新扫码不会解除”；不允许从应用内跳过。
- **挂机设置**：顶部“应用对象：账号名”，每个账号独立保存；外观标注为全应用设置。
- **非活动/失效状态**：中性横幅“此账号当前未运行，数据停在 X 前”，操作禁用并显示原因；登录失效单独提示“重新扫码”，不影响其它账号。

设计稿同时展示了第二期的“同时挂机”总开关与逐账号开关。第一期已隐藏这一分组，等第二期审批后再启用；账号管理、免扫码切换、每账号总览和设置作用域已在第一期实现。

关键交互规则：

- **查看无副作用**：顶部标签、总览卡片和“打开总览”只改查看，不启动/停止连接；未运行账号显示上次快照并标记陈旧。
- 单账号模式：侧栏切换器和顶部标签都只改查看；账号页及汇总卡片的“切换并挂机”经确认后才停止旧账号、启动新账号；界面明确提示会短暂中断看播，但不扫码。
- 同时挂机：切换标签只改变查看；只有“参与同时挂机”开关改变运行集合。
- **参与 ≠ 暂停**：关闭正在运行账号的参与开关时先确认会停止连接；打开参与开关不会清除该账号的暂停状态，暂停中的账号恢复后才开始。
- **全局暂停是覆盖层**：暂停时不改写各账号的 `paused`；恢复只恢复暂停前运行集合中仍有效且未单独暂停的账号。
- **保护暂停不可绕过**：重新扫码、重启应用、重新添加账号都不会解除；必须先在平台完成验证或等待冷却。
- **退出登录 ≠ 移除账号**：退出登录保留账号行与全部本地数据，只需重新扫码；移除账号移出列表并把关注/设置/任务额度/保护记录转入 `.retained`。
- “全部”页只做汇总与全局检查/暂停；单个账号的补齐、重连、退出登录、移除仍回到账号作用域。
- “全部检查/全部暂停”只作用于正在运行的账号；未运行账号不会因为汇总页的操作被唤醒并产生额外请求。
- 所有对话框（切换、退出登录、移除、风险确认、退出应用）都要求确认，Esc 可关闭，Tab 焦点限制在对话框内，关闭后焦点回到触发按钮。

## 8. 验收标准

**功能**

- 两个合成账号 A/B：A→B→A 切换全程不出现二维码；A 的关注、设置、任务进度、今日额度完整保留。
- 同一主播同时出现在 A/B 的关注列表时，两个账号的状态、操作和通知不串。
- A 登录失效时只标记 A；B 仍可运行/切换；重新扫码 A 不影响 B。
- 移除 A 后 B 的绑定、预算、保护记录不变；重新添加 A 能恢复关注与任务额度。
- 新账号默认空关注列表，不会自动挂机默认主播。

**安全**

- 账号列表、快照、日志、桥接响应均不含 `SESSDATA/bili_jct/qr_login_context/cookie`。
- 列表路径不触发 DPAPI 解密；切换只解封目标账号。
- 端点拒绝非注册表 id、路径与任意 URL。
- 迁移/切换崩溃后可恢复；旧根可回滚；无明文临时文件。

**UI**

- 切换器可用键盘操作，Escape 关闭，焦点返回触发按钮；确认对话框内 Tab 不逃逸。
- 非活动账号明确显示“未运行/数据停在 X 前”，不把旧数据显示成实时。
- 登录失效、保护暂停、全局暂停、切换中、退出中都有明确文案与下一步操作。
- 单账号与同时挂机两种模式的“切换查看”和“参与挂机”行为不会混淆。
- 全局暂停恢复后只恢复原运行集合，单独暂停的账号仍保持暂停。
- 退出登录后账号仍以“登录失效”保留，关注/任务/额度/保护记录可继续使用；移除账号不会清除这些状态。

**第二期**

- 3 个账号 × 2 个在播房间浸泡 2 小时，内存/CPU/进程数在预算内。
- 一个账号保护暂停或登录失效不会停止其它账号。
- 多个账号同一检查周期不会同时 probe；429/-412 会触发全局退避，而不是继续放大请求。

## 9. 审批结论与第一期落地范围

用户已批准“先做第一期，第二期单独审批”。第一期按推荐决策实现：

- 关注列表、设置、任务进度与保护记录按账号独立；允许不同账号关注同一主播。
- 主题与开机启动为应用级设置；任务开关、运行模式和暂停按账号独立。
- 顶部标签与账户卡片只切换查看；侧栏切换器也不改变运行集合；「切换并挂机」经确认后停旧账号、启目标账号，全程不扫码。
- 区分「退出登录」（保留账号行与数据）和「移除账号」（移到 `.retained`，同 UID 重新添加时恢复）；新账号关注列表默认为空。
- Tk 兼容界面只显示当前活动账号；多账号管理在 WebView2 界面提供。
- 同一时间只有一个活动账号；并发总开关、逐账号参与开关和多 Engine 同时激活均留待第二期，界面不展示。

第二期启动前仍需单独确认上限、错峰与风控预算；本文的并发章节是设计依据，不代表已实现。
